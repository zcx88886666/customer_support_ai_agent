# Cross-role terminal-state development evaluation — 2026-10-03

The new [versioned development dataset](../../evals/datasets/business_workflows_v1.jsonl) has four original synthetic cases: approved refund and idempotent retry, failed warehouse inspection, stale proposal after a second return, and cross-customer denial. [The runner](../../evals/runners/run_business.py) creates a separate SQLite database for each case, replays customer, warehouse, and supervisor actions through role-checked HTTP endpoints, invokes the controlled worker function across committed requests, and writes `manifest.json`, `case_results.jsonl`, `summary.json`, and `report.html` under ignored `evals/reports/<run_id>/`.

The `business-v1` scorer compares every HTTP step status and final return, proposal, approval, ledger, order version, and audit state with JSONL gold. It independently checks return ownership, approval before refund, one worker issuance with zero replay issuance, correct paid allocation, valid approval and inspection evidence, and refusal of a stale proposal. A deliberately disabled worker causes the approved-refund case to fail the terminal-state gate.

Actual result: **4/4 cases passed**, zero critical failures, and a passing local gate. The full Python suite passed **58 tests**; the separate 25-case chat smoke suite passed **28/28 executions**. Reproduce with `.venv/bin/python evals/runners/run_business.py` in `AUTH_MODE=mock`; results are emitted under the ignored report directory. These four cases are development fixtures, not a human-reviewed locked set. This runner uses local mock role headers and SQLite for speed. Separate OIDC browser and PostgreSQL checks cover the same business path, but the runner still needs a real-OIDC, isolated-PostgreSQL mode and wider cases before it meets the v6 evaluation target.
