> Verified 2026-10-03. This page reports repository evidence, not v6 design targets. The approved design remains in [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md) and [v6](../plans/resolveai-v6.md).

## Current snapshot

- Git was initialized; the initial implementation commit is `cd94ed7` and the local Prompt catalog commit is `ed6f457`. [release-v1](../prompts/releases/release-v1.json) locks the catalog commit and every catalog SHA-256. A complete Git bundle was verified and restored to a separate `/tmp` checkout at `cd94ed7`, where PromptRegistry accepted the release. The catalog, not Langfuse Cloud, supplies runtime Prompt text.
- A FastAPI/SQLAlchemy after-sales service, Alembic migrations, a LangGraph parent graph with read-only policy and order specialist subgraphs, a no-key mock mode, OIDC verification code, a Commerce MCP service, a controlled refund worker, Next.js UI, and Compose definitions are present.
- Local checks passed: **41 Python tests** (including 1,000 generated refund allocations, signed OIDC/MCP checks, model evidence source validation, [clarification expiry and task scope](implementation/clarification-2026-10-02.md), [bounded order/policy Replan](implementation/replan-2026-10-02.md), [historical policy rollback](implementation/policy-rollback-2026-10-02.md), deadline alerts, a cross-role HTTP refund workflow, checkpoint turn isolation, strict model schema validation, and telemetry filtering/masking/usage), **25 unique synthetic smoke cases / 28 executions**, a **Next.js production build**, **four Playwright role views**, and an isolated [OIDC browser return-to-refund journey](implementation/browser-workflow-2026-10-02.md). A [redacted smoke summary](implementation/mock-smoke-2026-09-29.json) is committed; the full local report is generated under ignored `evals/reports/<run_id>/`.
- The synthetic generator produced and independently validated **100,000** and **1,000,000** orders, with zero violations reported by its CSV validator. The complete 100,000-order world was imported by `COPY` into temporary PostgreSQL 16 in 6.508 seconds. The million-order world was imported into an isolated Docker PostgreSQL 17 database in **122.533 seconds**; six database quality checks reported zero violations before and after a [measured 20/50/100-user no-key API load](implementation/million-order-load-2026-10-02.md). See also the [measured data report](implementation/data-generation-2026-09-29.md) and [PostgreSQL integration report](implementation/postgres-integration-2026-09-30.md). Generated CSVs remain ignored.
- A real PostgreSQL 16.15 server with pgvector 0.6.0 passed clean migrations, a vector operation, the cross-role refund flow and retry, and the 100,000-order import. Docker Compose also ran with PostgreSQL 17.11 and pgvector 0.8.6: migrations, 25-order seed, chat, cross-customer denial, refund ledger, API restart, and OTel→Jaeger trace passed. The new [PostgreSQL policy search](implementation/policy-search-2026-10-02.md) indexed four active clauses, passed live draft indexing and bundle isolation, and rejected a stale index. A single live OpenRouter GPT-4o-mini structured-intent request passed after correcting the strict JSON schema; the key remains only in an ignored local file. See the [model integration report](implementation/openrouter-integration-2026-10-02.md). Langfuse US authentication, six prompt mirrors, dual trace export, masking, generation usage/cost, and a setup score passed; see the [Langfuse report](implementation/langfuse-integration-2026-10-02.md). Keycloak code+PKCE login, authenticated MCP reads and agent calls, cross-customer/role denials, and four real-browser role views passed; see the [OIDC/MCP report](implementation/oidc-mcp-integration-2026-10-02.md). Broader real-model evaluations, Mem0 A/B, and load tests remain open.
- An isolated Docker PostgreSQL 17 [refund worker recovery check](implementation/refund-worker-recovery-2026-10-03.md) forced two workers to wait on one order lock. Both observed one ledger, one issuance audit, and one balance change. A flushed but rolled-back second refund was recovered by a new worker run; a separate worker process issued nothing further.
