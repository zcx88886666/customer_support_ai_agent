# Human support ticket completion — 2026-10-06

The existing handoff created a ticket, and a supervisor could assign it, but the assigned support agent could not respond or close it. This slice uses the existing `ConversationMessage` table, so no database migration is needed.

When a new handoff ticket is created, it stores the customer's triggering message in the local database. Customers can list and read only their own tickets and add messages while open. An assigned support agent can read and reply to that ticket, then resolve it with a final written response. Supervisors can list and inspect tickets and assign open ones to a support actor. Each new message, assignment, and resolution is audited. Inaccessible ticket IDs return 404; closed tickets reject writes with 409. Multiple-role tokens get the union of read permissions, while support writes still require the exact assignment. Ticket detail holds a row lock while it reads messages so reassignment cannot expose later messages to a former assignee. The web UI exposes these actions for the three roles and clears ticket state when the actor or role changes.

Ticket resolution does not change return eligibility, warehouse inspection, a refund proposal, supervisor approval, or the simulated refund ledger. The manual decision and exception path for an ineligible or disputed return still needs a separate policy and implementation. This workflow also has no notification delivery, SLA queue, or reopen action; a subsequent chat handoff creates a new ticket.
