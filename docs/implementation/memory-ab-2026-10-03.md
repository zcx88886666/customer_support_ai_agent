# Isolated memory A/B and PostgresStore application check — 2026-10-03

The [40 versioned synthetic two-session stories](../../evals/datasets/memory_stories_v1.jsonl) exercise ten retained preferences, ten corrections, ten consent withdrawals, and ten requests without consent. The [runner](../../evals/runners/run_memory_ab.py) applied the same confirmed-preference/consent envelope to both candidates in a separate Docker PostgreSQL 17 database. PostgresStore received the confirmed structured key and value through a thin writer; Mem0 OSS 2.2.1 received the corresponding natural-language utterance with its normal inference path, local FastEmbed `sentence-transformers/all-MiniLM-L6-v2`, pgvector, and `openai/gpt-4o-mini-2024-07-18` through OpenRouter. This distinction makes the results an application-level candidate comparison, not a claim that the same extraction algorithm was tested twice.

The scorer reopened each store before reading. It checked the expected value in the top three results, removal of the old value after correction, empty results after consent withdrawal, namespace ownership, and empty shadow-user searches. For Mem0 it additionally inspected the local SQLite history database because deleting pgvector rows alone does not establish full deletion. `MEM0_TELEMETRY=false` was set before import. All data and prompts in this run were synthetic. Detailed local results and the dataset hash are under ignored `evals/reports/20261004T002027Z_memory_ae58f0/`.

Mem0 created two memories for every correction, leaving the superseded value retrievable. Its `delete_all(user_id=...)` removed the vector results for all ten withdrawn users, but each original utterance remained in its local `messages` history table after restart. Those are safety-gate failures for this configuration. The 20 passing Mem0 stories were retention and no-consent cases. The provider reported cost for all 40 model calls; the local embedding model had no provider charge. Timings are single-run local observations, not throughput guarantees.

The authenticated [PostgresStore adapter](../../apps/api/resolveai/memory.py) now mirrors only explicitly confirmed, allowlisted preferences into the same PostgreSQL transaction as the structured profile and audit. The server-derived customer ID fixes the namespace; callers cannot choose another customer's namespace through the profile API. Profile reads compare PostgresStore with the structured authoritative table and return 503 on drift. Startup reconciles only customers with memory entries or existing memory namespaces. The Compose API selects `LONG_TERM_MEMORY_MODE=postgres_store`; the no-key SQLite fallback stays `off`. Mem0 remains an offline comparison dependency and is not in the runtime image. The structured SQL table retains a revoked row for audit and reactivation checks, but the value is no longer retrievable through the application or PostgresStore; physical erasure of that table is a separate privacy-policy decision.

An isolated PostgreSQL 17 [application check](../../scripts/verify_memory_store_postgres.py) passed seven checks through mock-auth HTTP profile endpoints and direct database inspection: denial without consent and confirmation, owned correction, 503 on injected store drift followed by reconciliation, rollback of both stores in one transaction, deletion and consent withdrawal, restart and cross-user isolation, and no retrievable store row afterward. The rebuilt Docker API started with `LONG_TERM_MEMORY_MODE=postgres_store` and HTTP health 200. A separate [real Keycloak OIDC check](../../scripts/verify_memory_oidc.py) passed role denial, consent/confirmation/correction/cross-customer isolation, deletion, and restoration of the original synthetic demo profile. The full Python suite passed **63 tests**, and the 25-case chat smoke suite passed **28/28 executions**. A browser UI memory journey and sustained write load remain open.

