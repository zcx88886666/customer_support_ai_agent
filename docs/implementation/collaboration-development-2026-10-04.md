# Twenty-case collaboration development comparison — 2026-10-04

`collaboration_dev_v1.jsonl` contains 20 original synthetic composite questions across five template families: undelivered returns, delivered windows, product exceptions, warehouse inspection, and refund policy. Each case is run twice through the same mock-auth HTTP API, once with `agent_mode=single` and once with `agent_mode=collab`, in randomized order. Every execution starts with a fresh SQLite demo world. The existing `smoke-v2` database-first scorer checks both specialist findings, current owned evidence, money safety, route, and any required answer text. The runner records execution order, dataset and Prompt hashes, per-case provider usage, tokens, tool calls, handoffs, dispatch/evidence errors, latency, paired outcomes, and family counts in ignored local reports.

The first live GPT-4o-mini run (`20261004T090756Z-collab-live-ec74c0`) passed **12/20 in each mode**. Eight pairs missed one requested read domain because the model sometimes labeled mixed logistics/policy text as only logistics or only policy. A bounded server rule now keeps both explicit read domains. The corrected run (`20261004T091357Z-collab-live-a08cdb`) passed **20/20 in each mode**, but its early report omitted detailed token/tool metrics. After adding those metrics, `20261004T091845Z-collab-live-52ae7e` scored **19/20 single, 20/20 collab**: the model omitted a refund intent in a read-only refund-policy question, causing a safe human handoff. A narrow informational-policy route preserved the safety guard for direct refund actions. The next run (`20261004T092321Z-collab-live-648655`) again scored **19/20 single, 20/20 collab**: both specialists returned valid evidence, but answer assembly omitted the supervisor-approval explanation when the model supplied only read intents. The answer now includes that factual explanation for explicit refund-policy inquiries; a regression test checks two findings, the approval text, and an empty refund ledger.

The final live report `evals/reports/20261004T092728Z-collab-live-d7529e/` passed **20/20 single and 20/20 collab**, with 20 success ties and zero handoffs, dispatch errors, evidence errors, or critical failures. Both modes made 57 provider calls and 40 specialist tool calls. Single used 12,266 input and 1,550 output tokens, cost **$0.0027699**, with P50/P95 **4,671.74/6,020.20 ms**. Collab used 12,266 input and 1,592 output tokens, cost **$0.0027951**, with P50/P95 **3,488.64/5,087.52 ms**. These are provider-reported costs for this one development run. The final mock report `evals/reports/20261004T092707Z-collab-mock-1f20ca/` passed all 40 executions without a key. The full Python suite passed **79/79**, the 30-case smoke suite passed **33/33 executions**, and the rebuilt Docker API returned `/health` 200.

This set was authored while implementing the system and refined after inspecting failures. It is a useful regression fixture, **not independently reviewed locked gold**. Similar questions share templates and seeded orders; 20 rows are not 20 independent customer conversations. The single/collab success tie and small latency difference do not establish a production quality or performance advantage. Broader terminal-state gold, human review, and locked paired evaluation remain open.

The `single` path currently runs the same read-only specialist logic sequentially; `collab` fans out the tasks. This paired result measures dispatch and execution behavior for those paths, not quality differences between separate reasoning models. A [separate single-domain suite](collaboration-single-domain-2026-10-04.md) checks over-dispatch, and a [paired fault suite](collaboration-faults-2026-10-04.md) checks injected specialist failures.

After the live measurement, the paired runner began capturing one `seed_clock` for every fresh database in a run and recording it in the manifest and case rows. The composite mock report `evals/reports/20261004T095848Z-collab-composite-mock-30aeb3/` passed 40/40, and every row matched the one manifest seed timestamp. The earlier live measurements used a fresh seed timestamp per execution; their costs and outcomes remain as recorded, but they are not evidence of exact fixture-clock equality. The application wall clock is not frozen by this runner.
