# Automatic direct return review — 2026-10-07

For a confirmed request by an owning customer, `POST /returns` now routes `outside_window`, `product_exception`, `delivery_unverified`, and `unsupported_order` results into the existing eligibility-review ticket workflow. It returns HTTP 202 with `status=human_review`, `ticket_id`, and `reason_code`. The operation creates no return or refund. Valid requests still return the committed return ID. Invalid and overcommitted quantities, missing or foreign orders/items, and unconfirmed requests remain errors. `POST /returns/review` remains available for an explicit review request; Agent chat still reports its own policy denial without creating a ticket.

The direct route serializes on the customer row, reuses an existing review ticket for an exact key and payload even if policy facts later change, and uses the existing ticket audit and ownership checks. The chat return path now takes the same customer lock, so a return and review on different orders cannot both commit under one customer/key. The two paths reject a key already used for the opposite outcome. The return-side guard reads the review creation audit so `create_return` also works against the earlier migration schema that lacks `tickets.review_key`. The web form now shows the ticket outcome and shares an idempotency key across its normal and explicit review buttons for the same form values. Support resolution does not create a return or authorize a refund.
