# Warehouse receipt discrepancy handoff — 2026-10-06

Warehouse staff can report an observed quantity different from the requested return quantity with `POST /warehouse/returns/{return_id}/receipt-dispute` or the warehouse form. The request requires a nonblank note and the warehouse role. It locks the return row, creates one customer-owned linked ticket with a warehouse message, records return and ticket audit events, and sets the return to `exception` in the same transaction. An exact retry returns the same ticket, including after support closes it; a changed count or note is a conflict. A normal receipt and a discrepancy report serialize on the same return row.

The customer can see the exception state and ticket. A supervisor can assign the ticket, and the assigned support actor can reply and resolve it. Resolving the ticket is a communication action only: the return stays in `exception`, with no receipt, inspection, proposal, approval, or refund ledger. A later evidence-based reversal or exceptional disposition would require a separate reviewed business workflow. Warehouse staff should not use the ordinary receipt action to overwrite a disputed count.

A first review found that blocking receipts only while a ticket was open let a generic support reply release the return, and that a later failed inspection would collide with the unique ticket link. A regression reproduced the missing exception state. The revised atomic exception transition closes both paths; a second review found no Critical or Important issue in this workflow.
